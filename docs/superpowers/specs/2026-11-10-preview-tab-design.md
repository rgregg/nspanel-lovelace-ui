# Preview tab for the add-on editor - design

## Intent and why

The add-on's web editor has two tabs, "Visual editor" and "YAML editor".
Today the only way to see what a card will look like is to save, apply, and
walk to the panel. Add a third tab, "Preview", that shows an approximation of
what the panel's 320x480 portrait screen (US portrait model, `us-p`) will
display for the draft configuration, using the user's real current Home
Assistant states, so a config can be checked before it is deployed.

The user's bar (their words): it only matters if the rendered version and the
preview are "considerably different from each other". Close, not pixel-exact.

## Goals

- A "Preview" tab beside the existing two tabs in `frontend/index.html`.
- Cards covered in the first version: `cardEntities`, `cardGrid`, and the
  screensaver. Nothing else.
- Content (text, icon choice, on/off state, colours, values, weather) comes
  from the add-on's own card code run against the draft config, not from a
  second implementation of that logic. The preview must not be able to drift
  on content when a card's backend logic changes.
- Entity values are the user's real current states (from the backend's existing
  Home Assistant connection), not sample data.
- Previews the unsaved draft (what is in the editor), not only the saved file.
- The user picks a panel and steps through its cards plus the screensaver.

## Non-goals

- Other card types (media, thermo, alarm, QR, power, unlock), popups, the
  startup page.
- Touch interaction, navigation between cards by tapping, live animation, or
  pushing updates while the tab is open (refresh on demand or on tab open is
  enough).
- Pixel-exact fonts or anti-aliasing. Nextion fonts cannot be used in a
  browser; a close web font is acceptable.
- Models other than `us-p` in the first version (a layout for each model is
  later work), though the design should not hard-code `us-p` into the
  renderer's data model.

## Anti-goals

- The preview must never publish to MQTT or otherwise reach a real panel, even
  by accident. Rendering must use a capturing fake output, not the live panel
  queue.
- No separate hand-written reimplementation of what each card says. If the
  preview and the panel can disagree about content, the design has failed.
- Must not break or slow the running panel (no heavy work on the panel's
  threads; the preview is read-only against the HA state cache).

## Constraints

- Repo: fork `rgregg/nspanel-lovelace-ui`, add-on under
  `nspanel-lovelace-ui/rootfs/usr/bin/mqtt-manager`. GPL-3.0. Work on branch
  `preview-tab`, branched from `filtered-entity-subscription` because the
  preview relies on its lazy per-entity subscription (entities named in an
  unsaved draft are not yet subscribed).
- Editor server `web.py` and the card backend `main.py` are separate s6
  services (`nspanel-editor`, and the main service), so separate processes.
  Only the main process holds the Home Assistant state cache
  (`libs/home_assistant.py`).
- The editor's Content-Security-Policy is `default-src 'self'; script-src 'self';
  style-src 'self'`. New JS, CSS, fonts and images must be served by the editor
  itself from `frontend/`; no inline scripts or styles, no CDN.
- The editor's auth must apply to any new endpoint (Supervisor-ingress peer
  check, or standalone basic auth). Request-size and content-type checks in
  `do_POST` apply too.
- Commits authored as Ryan Gregg with no Claude attribution lines of any kind
  (his explicit instruction); no Co-Authored-By.
- Tests live in `tests/`; keep the existing suite (76) passing and add tests
  for the new code.

## How it gets made (what was decided)

Decided by the user:
- Tab named "Preview", beside Visual editor and YAML editor.
- Real current states.
- Entities, grid, screensaver first.

Recon findings (facts, not decisions):
- Cards are generated by `ha_cards.py` (`card_factory`, `EntitiesCard`,
  `Screensaver`, ...). Each ends in a text command sent through
  `libs/panel_cmd.py` (`entityUpd~...`, `weatherUpdate~...`, `time~`, `date~`,
  and so on) onto a per-panel `msg_out_queue`. The Nextion screen firmware, not
  the add-on, draws the layout from those strings.
- Layout sources for the screen are in the repo's `HMI/` directory
  (`HMI/n2t-out-visual/cardEntities.txt`, `cardGrid.txt`, screensaver pages,
  `HMI/code_gen/pages`, `HMI/fonts`, icon data under `HMI/code_gen/icons`).

My calls (the user has not weighed in on these):
- **Where rendering runs:** in the main process, which has the state cache.
  Add a small loopback-only HTTP endpoint (or equivalent) there that accepts a
  draft config plus a panel name and returns the captured commands per card.
  `web.py` proxies `POST /api/preview` to it and applies the editor's normal
  auth. Rationale: avoids duplicating the HA connection in the editor process.
- **How cards are rendered offline:** build each card through the normal
  `card_factory` with a fake panel object whose `msg_out_queue` is a capturing
  list, then read the commands. No real panel, MQTT, or navigation is touched.
- **Frontend:** a new `frontend/preview.js` and styles in `style.css` draw the
  captured commands into a 320x480 DOM/canvas "screen" using a layout table
  transcribed from the `HMI` sources. Icons use a locally served Material
  Design Icons webfont (licence permitting) mapped through the add-on's icon
  mapping. Fonts: a close web font served locally.
- **Staleness:** the tab renders when opened, when the selected panel or card
  changes, and on a Refresh button, from the current draft.
- **Unsubscribed entities:** use the existing lazy tracking and wait a short,
  bounded time for first values; render "unavailable"-style placeholders if
  they have not arrived rather than blocking.

## Left to the builder

- Exact endpoint shape, port, and how the main process hosts it.
- Exact fake-panel interface needed by `card_factory`.
- The layout table's data format and how closely each element's position and
  size match the HMI source.
- Font and icon-font choices and how they are bundled.
- How to handle a draft that fails config validation (show the error).
- Test approach, including a golden-output comparison against known commands.

## Success

For a representative panel (the user's: a Lights `cardEntities` card, a
`cardGrid`, and the screensaver with weather), the preview shows the same text,
icons, states and colours the panel will show, laid out recognisably the same.
When the physical panel is back, a side-by-side check should show no
considerable differences. Verified by tests plus a live check on the user's
HA.
